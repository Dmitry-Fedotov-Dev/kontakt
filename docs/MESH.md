# Kontakt Mesh — план и состояние

Спецификация: «Kontakt — Distributed Voice Mesh» (разделы §0–§50). Здесь — как она
ложится на код, по фазам. Главный принцип (§50): ёмкость и качество **меряются**,
а не предполагаются. Ни одной константы вида «Cloudflare = 25 Мбит/с» (§47).

## Слои

| Слой | Что | Где |
|---|---|---|
| Control plane | Master: реестр узлов с TTL, приём (admission), выдача соседей | `internal/mesh` (`registry.go`, `master.go`) |
| Mesh core | идентичность, доверие, транспорт, измерения, топология, маршруты, failover | `internal/mesh` |
| Data plane | RTP между Worker'ами по выбранному маршруту | фаза 2 |
| SIP | REGISTER/AOR/Contact/NodeID, звонок через mesh | фаза 2–3 |
| Edge | браузер по WebRTC DataChannel, Android-обёртка WebView | фаза 4 |
| OpenWrt | пакет `kontakt-worker`, LuCI | фаза 5 |

Станция-рулетка (web/signal/media) остаётся как есть и становится одним из
потребителей mesh: её media-узел — это Worker с медиа.

## Фазы

**Фаза 1 — control plane и маршрутизация — СДЕЛАНО**

- §7 идентичность: ed25519, `NodeID` = хеш открытого ключа, ключ в файле `0600`,
  переживает перезапуск, наружу не уходит. Edge — эфемерная.
- §8 доверие: `UNKNOWN → AUTHENTICATED → KNOWN → AUTHORIZED → CONNECTED`.
  AUTHENTICATED — подпись рукопожатия проверена; KNOWN — узел есть в реестре или в
  локальном списке; AUTHORIZED — допуск, подписанный Master'ом (ключ Master'а
  закреплён у Worker'а), или узел в локальном списке доверенных. Допуск имеет срок
  и проверяется **без** Master'а — поэтому его отказ не рвёт связи (§6).
- Все управляющие сообщения подписаны; защита от повтора — монотонный номер и окно
  по времени.
- §16 транспорт — интерфейс; реализации TCP и WebSocket. Тип пути (`direct`,
  `websocket`, `cloudflare`, `webrtc`) — свойство ребра топологии (§46).
- §9–§10 реестр и heartbeat с TTL, состояния HEALTHY / DEGRADED / OFFLINE.
- §11 обнаружение ограничено: Master отдаёт не больше `max_peers` соседей.
- §12 измерения на каждом ребре: RTT, потери, джиттер, время жизни связи.
- §13 `RouteScore` с настраиваемыми весами; пороги warning/critical (§25).
- §14 топология ограничена: `max_hops`, TTL объявлений, версия, рассылка только
  изменившегося.
- §15 failover: primary + 2 альтернативы; восстановившийся маршрут сначала
  проходит испытательный срок (N хороших замеров подряд).
- §18, §24 ёмкость по факту: `NetworkCapacity{ObservedMbps, AvailableMbps,
  Utilization, ActiveSessions}`, звонков = свободная полоса × (1 − запас) / полоса
  звонка по замеру. Пока замера нет — плановые 400 кбит/с (§23), и это видно в
  метрике как «оценка», а не факт.
- §19 метрики `cloudflared` (`cloudflared_tcp_total_sessions` и др.) читаются, если
  задан адрес его `/metrics`.
- §38 метрики узла.

Код: `internal/mesh`, бинарник `cmd/kontakt-node` (роли master / worker / standalone,
админка `/metrics`, `/mesh/status`, `/mesh/route`). Проверено тестами: криптография
и доверие, пробы, ёмкость (пример §24), маршрутизация (пример §39), альтернативы,
failover с испытательным сроком, ограниченная топология; сквозной тест на TCP —
Master + 4 Worker'а: обход ребра с потерями, отказ Master'а без разрыва связей, отказ
ретранслятора с failover, вход нового Worker'а, отказ чужому узлу и неверному токену,
старт без Master'а через доверенный Worker. Живыми процессами — то же, руками.

Найдено тестами и исправлено по ходу: строгий рост номера сообщений ронял пробы при
записи из нескольких горутин (теперь окно повтора, как в IPsec); последнее объявление
умершего узла держало маршрут через него (теперь двусторонняя проверка рёбер);
опоздавший ответ на пробу засчитывался как RTT; отказ маршрута «в никуда» не
считался отказом; `Close` Master'а зависал на соединениях регистрации; разбор
метрик cloudflared терял строки без меток.

Ограничения фазы 1: управляющий канал подписан, но **не шифруется** (целостность и
подлинность есть, конфиденциальности нет — токен по сети не идёт, только HMAC); полоса
узла считается по счётчику, который подаёт медиа-слой, — в фазе 1 его подключать не к
чему, и `kontakt_call_bandwidth_measured` честно показывает 0. Бинарник для MIPS —
7 МБ: для роутеров с 16 МБ флеша в фазе 5 понадобится ужатие.

**Фаза 2 — data plane**: пересылка RTP Worker → Worker по маршруту, смена маршрута
посреди звонка, SIP Registrar (§28) и звонок до абонента на другом Worker'е (§29).

**Фаза 3 — нагрузка по §41–§43**: Master + 5 Worker'ов, 10…200 звонков через
xk6-sip, отчёт в формате §43. Отдельно — вариант с `cloudflared` (§42).

**Фаза 4 — Browser Edge (§31–§33)** и Android-обёртка WebView (§34).

**Фаза 5 — OpenWrt (§35–§37)**: пакет, init-скрипт, UCI-конфиг, затем LuCI.

## Чего НЕТ и почему

- Автоматического выбора Master'а нет (§6) — осознанно, по спецификации.
- Полного графа сети у узла нет и не будет: только `max_hops` вокруг себя (§14).
