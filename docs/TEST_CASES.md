## Подготовка (один раз)

```bash
git pull
go build -o bin/ ./cmd/...                 # web, signal, media, loadgen, kontakt-node
```

На Windows всё запускается **в WSL** (`wsl`, затем `cd /mnt/d/Coding/kontakt/kontakt`): команды
вида `X=1 команда` — синтаксис bash, PowerShell их не понимает.

Части стенда — их можно держать запущенными одновременно, порты не пересекаются:

| Что | Команда | Порты |
|---|---|---|
| Станция (рулетка) | `IP=<IP машины> SIP_UDP=:5060 ./scripts/run.sh` | web `:8080`, signal admin `127.0.0.1:8091`, media `127.0.0.1:8082`, SIP `:5060` |
| Mesh (Master + 5 Worker'ов) | `./scripts/mesh-demo.sh` | Master admin `127.0.0.1:7401`, Worker'ы `127.0.0.1:7421…7425` |
| Станция за туннелем | `MONITORING=1 ./scripts/cluster-tunnel.sh` | ссылка `https://….trycloudflare.com` в выводе; порты от 27580, Grafana 27630, Prometheus 27631 |
| Радио | `TUNNEL=1 bash scripts/radio.sh` | `http://localhost:27620` и ссылка туннеля в выводе |
| Мониторинг отдельно | `monitoring/stack.sh up` (порты: `GRAFANA_PORT=… PROMETHEUS_PORT=…`) | сам выбирает Docker / Docker Desktop / без Docker |

NodeID узла демо-стенда: `bin/kontakt-node -identity data/mesh-demo/w3.key -print-id` (w1 = vps-almaty,
w2 = home-router, w3 = office, w4 = phone-termux, w5 = vps-bishkek). PID узла — в выводе
`mesh-demo.sh`.

### B-2. Два человека соединяются и слышат друг друга
- **Шаги:** открыть `http://localhost:8080` в **двух разных браузерах** (или обычное окно +

- **Ожидается:** первый, пока один, слышит гудки; после снятия трубки вторым оба слышат друг
  друга в обе стороны, задержка на слух незаметна; голос «окрашен» линией 32 (выбора линии на странице нет). Кнопки круглые: при нажатии на 1 с становятся вдавленными, затем возвращаются.
- **Автотест:** `e2e TestRouletteFlow`, `k6/functional/pair.js` (CI).
- **Итог:** частично ✅ 04.10.2026 — xk6-sip `pair.js` (софтфоны по SIP/UDP): A слышит B (score 0,822), B слышит A (0,777), себя не слышат (≤ 0,19), провалов 0 мс. Двумя людьми в браузерах — не проверено.

### B-3. Собеседник ушёл — следующий, в том же звонке

## Критические

### C-1. Жалоба: жёлтая карточка, затем бан
- **Подготовка:** новые браузеры — новички, их жалобы в зачёт не идут (это MOD-3). Для этого
  кейса в `config/kontakt.json` — `"trust_talks": 0` (применится на лету), после — вернуть 3.
- **Шаги:** A и B соединены (B-2). В A **ban** → **sure?**. Затем B снять трубку снова, C
  (третий браузер) соединяется с B и тоже жалуется.
- **Ожидается:** после первой жалобы B получает жёлтую карточку и уходит искать дальше, A
  видит «Собеседнику выдана жёлтая карточка»; A и B больше не соединяются друг с другом.
  Жалоба второго, **другого** человека (C) — вечный бан: у B нет кнопки **pick up**. Повторная
  жалоба того же A карточку не добавляет.
- **Автотест:** `e2e TestYellowCardThenBan`, `TestHotConfigInstantBan` (`ban_reporters: 1`).

### T-3. Обновление без смены адреса
- **Шаги:** стенд `./scripts/cluster-tunnel.sh` запущен; во втором окне — `./scripts/cluster-tunnel.sh update`.
  Затем убить signal (`kill -9 <PID>`). Затем подложить ошибку компиляции и снова `update`.
- **Ожидается:** после `update` — «сервисы обновлены, адрес прежний», по старой ссылке станция и радио
  отвечают, `cloudflared` — тот же процесс; ведущий радио переподключается сам, звонки обрываются.
  После `kill` — «сервисы остановились — запускаю снова», адрес прежний. Неудачная сборка —
  «работает прежняя версия», сервисы не перезапускались.
- **Итог:** ✅ 04.10.2026 (WSL, Docker Desktop): все три сценария — signal с новым PID, `cloudflared`
  тот же, старая ссылка отвечает 200; при неудачной сборке signal тот же процесс.
